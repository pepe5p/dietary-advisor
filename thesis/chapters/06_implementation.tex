\chapter{Implementation: challenges and solutions}
\label{cha:implementation}

The previous two chapters described what the system is designed to do and why each technology was chosen. Turning that design into a working, evaluable system surfaced a number of problems that were not visible at the design stage. This chapter documents each of them as it was actually encountered: what went wrong with the first approach, what alternatives were considered, what was ultimately decided, and what that decision cost or gave up. Several of these problems recurred across design iterations before the final shape described in \Cref{cha:design} was reached, and a few avenues were investigated and abandoned outright; both are reported here, since a design's blind alleys are as informative as its final form. Read together, the sections below share a pattern worth stating in advance: almost every difficulty turned out to be a case of a component quietly producing something that looked right, and almost every solution consisted of removing the opportunity to be quietly wrong rather than adding an instruction not to be. A schema field was deleted so a number could not be invented, an absent nutrient value was made to report itself as absent rather than as zero, a reviewer was stripped of the ability to edit so that it had to state its objections, and the evaluation's own measuring instrument was doubled up so that its errors would become visible.

\section{Keeping nutrients out of the model's output}
\label{sec:impl-portion-ref}

The first design considered for the agent's output schema included a nutrient breakdown alongside every portion, on the reasoning that having the model state what it believed each ingredient contributed would make its intermediate reasoning inspectable. This was abandoned almost immediately: a schema field that accepts a nutrient value is a schema field the model can, and eventually will, fill with an invented number, no matter how the accompanying prompt text discourages it -- exactly the hallucination risk described in \Cref{sec:background-llm-failure-modes}. The schema was cut down to a bare reference: a database code, a human-readable name, and a gram quantity, with no room for a nutrient value anywhere. Any nutrient figure that ends up in the final report must therefore come from resolving that code against the real database (\Cref{sec:design-domain-model}), which is enforced mechanically by an output validator that resolves every code and raises a structured retry -- listing precisely which codes failed and reminding the model that a code must be copied verbatim from a prior lookup result -- if any of them fail to resolve. The cost of this decision is that the model can no longer show its own arithmetic; the benefit is that there is no field left in which it could hallucinate a number that later gets treated as ground truth.

\section{Completing the food catalogue}
\label{sec:impl-catalogue-completeness}

The first version of the food knowledge base used only Open Food Facts, on the reasoning that it is the larger, more actively maintained of the two sources considered in \Cref{sec:tools-food-data}. This surfaced a gap almost as soon as real recipes were attempted: Open Food Facts is a database of \emph{packaged} products, contributed by people photographing a label, so it has dense coverage of a specific brand of yoghurt but effectively no coverage of a raw carrot, a plain egg, or rolled oats bought loose -- exactly the generic, minimally processed ingredients most home recipes are built from. The USDA FoodData Central Foundation Foods and SR Legacy datasets were added specifically to close this gap, since they are curated around generic foods rather than branded products. The two sources are kept as separate tables behind one facade (\Cref{sec:design-food-db}) rather than merged into one, because their native schemas differ too much to usefully reconcile: a packaged product's brand, ingredient list and barcode have no analogue in a generic USDA entry, and forcing a shared schema would have meant discarding source-specific fields useful to the lookup tool's callers. The lookup tool queries both tables in parallel for every query and returns both sets of hits, leaving the choice between a specific branded product and a generic staple to the model, which is the party that actually knows which one the recipe calls for.

\section{Making hybrid search actually work}
\label{sec:impl-hybrid-search}

An initial, lexical-only search implementation performed adequately on queries that matched a product's name closely, but failed in two systematic ways once tested against the kind of vague, everyday query a language model tends to produce rather than an exact product name. First, near-synonyms with no shared word stem -- a query for ``courgette'' against a catalogue entry labelled only ``zucchini'' -- never matched at all, since a lexical ranking has no notion of two different words meaning the same thing. Second, and less obviously, an embedding-only alternative tested alongside it had the opposite failure: it would occasionally under-rank a nearly exact textual match against a food whose full description embedded slightly off-distribution (for instance, a product whose printed name is terse but whose full ingredient text pulls its embedding toward an unrelated cluster), because a single dense vector cannot always represent both a precise textual match and a semantic one equally well. Neither channel alone was reliable enough on its own; the combined channel described in \Cref{sec:tools-retrieval} and \Cref{sec:design-hybrid-search} -- reciprocal rank fusion over both rankings -- was adopted specifically because it recovers a food when either channel individually ranks it highly, without requiring the two channels' raw scores to be calibrated against each other.

A related, smaller decision concerned exactly which text is embedded for each catalogue entry. Embedding only the product name discarded useful signal that a name alone often does not carry (an ingredient list, a category, a brand); embedding the entire raw record, on the other hand, diluted the resulting vector with data-quality noise specific to a crowd-sourced dataset (repeated placeholder text, inconsistent formatting, occasionally entire other languages left untranslated in a description field). The document text embedded per entry was settled on as a curated concatenation of the fields most likely to carry the food's identity -- name, brand, category and, where present, a short ingredient summary -- rather than either extreme.

\section{Tool ergonomics under a limited context budget}
\label{sec:impl-tool-ergonomics}

An early version of the lookup tool accepted one query per call, mirroring how a human might type one search into a search box at a time. In practice this meant that composing a single day's meals, each needing several looked-up ingredients, required dozens of sequential tool round trips, each one adding its own request latency and consuming context-window space for the surrounding conversational scaffolding that a tool call and its result carry. The tool was changed to accept a batch of queries in one call, so that all of a recipe's ingredients -- or, in the more aggressive case actually used, all of a meal's ingredients -- could be looked up in a single round trip. A second, related change concerned the shape of the tool's response: an early version returned a natural-language summary of the top matches (``the best match for `mozzarella' is a 250g pack of...''), which read well but was harder for the model to parse reliably into exact codes and gram-scaled nutrient values than a compact, uniformly structured JSON result carrying the same information field by field; the response format was switched to structured JSON for this reason. Finally, because a lookup batch can, in principle, request an unbounded number of results, the number of hits returned per query was capped, trading a small risk of missing a marginally better match further down the ranked list for a predictable, bounded contribution to the context budget every lookup call makes.

\section{Partial nutrient coverage in the food catalogue}
\label{sec:impl-missing-nutrients}

Neither food data source has complete nutrient coverage for every entry: a crowd-sourced product record can be missing a fibre value because whoever transcribed the label did not include it, and even the curated USDA datasets do not report every nutrient for every food. The naive aggregation strategy -- treating an absent nutrient field as zero when summing -- was tried first and rejected quickly, because it produces a total that looks exactly like a real, complete measurement while silently understating it; a plan whose fibre total is reported as \qty{8}{\gram} because half its ingredients simply have no fibre data on file is indistinguishable, from the number alone, from a plan that genuinely contains \qty{8}{\gram} of fibre. This is precisely the kind of confidently wrong number the totaller exists to prevent, so treating an unknown as a false zero would have reintroduced, at the aggregation layer, the exact failure mode the aggregation layer is meant to eliminate.

The totaller instead tracks, per nutrient, which portions of the plan (by ingredient, and by the share of the plan's total mass they represent) have no recorded value for that nutrient, and reports the resulting total together with a coverage warning whenever any contributing food is missing data, naming up to three of the largest offending foods by mass so that a downstream reader -- either a human or, more importantly, the critic in the reflection loop -- knows which total to distrust and by how much. \Cref{alg:coverage} sketches the computation.

\begin{algorithm}[htbp]
\caption{Coverage-aware nutrient total with per-nutrient warnings}
\label{alg:coverage}
\begin{algorithmic}[1]
\Function{TotalWithWarnings}{$portions$}
    \State $totals \gets$ empty map from nutrient to exact rational sum
    \State $missingMass \gets$ empty map from nutrient to (total mass, list of foods)
    \For{each $portion$ in $portions$}
        \For{each $nutrient$ tracked}
            \If{$portion.food$ has a value for $nutrient$}
                \State $totals[nutrient] \gets totals[nutrient] + portion.food[nutrient] \times \frac{portion.grams}{100}$
            \Else
                \State record $portion.grams$ and $portion.food.name$ under $missingMass[nutrient]$
            \EndIf
        \EndFor
    \EndFor
    \State $warnings \gets$ empty list
    \For{each $nutrient$ with a nonempty $missingMass[nutrient]$}
        \State $\mathit{share} \gets$ missing mass as a fraction of the plan's total mass
        \State append a warning naming $nutrient$, $\mathit{share}$, and up to three foods from $missingMass[nutrient]$
    \EndFor
    \State \Return $(totals, warnings)$
\EndFunction
\end{algorithmic}
\end{algorithm}

The exact rational arithmetic chosen in \Cref{sec:tools-aggregation} is what makes this warning reliable in the first place: because every summed value is an exact fraction rather than a rounded float, a reported total is guaranteed to differ from a genuinely complete measurement only by the contribution of the foods explicitly listed as missing, never by an additional, silent rounding error compounding the understatement.

\section{Placing the totaller in the pipeline}
\label{sec:impl-totaller-placement}

Three placements for the totaller were considered before settling on the design in \Cref{sec:design-totaller}. Running it only as a post-hoc scoring step, entirely outside the generation pipeline, would have made it trivial to add and to disable, but would have given the model no way to see its own running totals while composing a plan, forfeiting most of the benefit of grounding at all: a model that cannot check its own homework mid-generation has no opportunity to correct an overshoot before committing to a final answer. Running it only as a hard, generation-blocking constraint -- refusing to accept a plan until its totals fall within a tolerance -- was also considered and rejected, because a hard numeric gate on a language model's output tends to produce a model that keeps calling the tool and adjusting portions in unproductive small increments near a decision boundary rather than converging, and because a plan that is a close but imperfect macro match is generally more useful to return than no plan at all. The totaller was instead exposed as an optional tool the model \emph{may} call as often as it likes while composing a plan, with its output also reused, unmodified, as grounding context for the critic during the reflection loop (\Cref{sec:design-reflection}) and as the independent scoring computation the evaluation harness applies afterwards (\Cref{sec:methodology-quantitative}) -- three uses of the same underlying computation, at three different points in the plan's lifecycle, none of which force the model's hand.

\section{Designing the critic}
\label{sec:impl-critic-design}

The first version of the reflection loop gave the critic the same tools as the nutrition agent, including the ability to look up further foods and to emit a fully revised plan directly, on the reasoning that a more capable critic should simply be able to fix what it finds wrong. This was reverted after observing that a critic with edit access tends to blur into a second, less carefully prompted nutrition agent: instead of pinpointing what was wrong with the existing plan, it would sometimes silently re-plan a meal from scratch, discarding parts of the original that were perfectly acceptable, which defeats the purpose of a targeted review step and makes the loop's behaviour harder to reason about and to evaluate. The critic was redesigned to be strictly tool-less and read-only, limited to producing a list of concrete issues (or an empty list); revision was moved entirely to a separate refiner role, structurally identical to the nutrition agent and explicitly instructed to address only the issues the critic listed with otherwise minimal changes. This division of labour is also what makes the totaller's grounding effective in the way described in \Cref{sec:design-reflection}: because the critic cannot itself call the totaller mid-review, it is instead handed the already-computed totals and coverage warnings directly, so its judgement of whether a macronutrient target has been met rests on a number it did not compute itself.

A second design question was how many refinement passes to allow before giving up, and what to do if the critic and refiner have not converged by then. An unbounded loop was rejected outright, since nothing guarantees a critic and refiner pair will ever agree, and an unbounded retry budget is incompatible with NFR4's requirement that a session complete in interactive time. A small, fixed iteration cap was chosen instead, with the loop falling back to returning the last refined plan, rather than failing the session, if the cap is reached with issues still outstanding -- a plan that a critic still has minor objections to is, in every case observed, still more useful to a user than no plan at all.

A third, open question -- whether the critic should use a different, stronger model than the one generating the plan, on the reasoning that a reviewer benefits from more capability than the party being reviewed -- was investigated only partially. The pipeline supports configuring a different model per role, but the ablation study in \Cref{cha:methodology} uses the same model for the critic and the generator throughout, to keep the number of independent variables in the experimental grid manageable; \Cref{sec:conclusions-future-work} returns to this as a direction for further work.

\section{Prompt-level fixes discovered through iteration}
\label{sec:impl-prompt-fixes}

A number of smaller problems surfaced only after reading actual generated plans rather than from any a priori design consideration, and were each addressed with a targeted prompt change rather than a structural one.

Early plans for users with no explicitly stated micronutrient concern nonetheless sometimes combined several implicit risk factors -- a vegetarian diet pattern together with a woman of reproductive age, say, which jointly imply an elevated iron requirement neither factor implies on its own -- without the plan's rationale acknowledging it. The nutrition agent's prompt was extended to explicitly instruct it to reason about implicit micronutrient interactions arising from a combination of profile factors, rather than only from any single factor in isolation.

Related to this, early plans treated the free-text rationale field purely as an explanation of the choices already made, leaving no natural place to mention that a nutrient target could reasonably be met only partly through food and would benefit from supplementation (vitamin~B12 alongside metformin, for instance). The rationale field's prompt instructions were extended to explicitly invite this kind of supplementation note where relevant, rather than requiring the model to either silently omit the concern or force an unrealistic amount of a food into a recipe purely to hit a number on paper.

A third recurring pattern concerned portion sizes that did not correspond to how a food is actually sold or used: a recipe calling for 90~g out of a 100~g pack, or 110~g when only 100~g is available, both of which are mildly implausible instructions for an actual shopper. Explicitly instructing the model to prefer using a whole package, or a simple fraction of one, measurably reduced this pattern, though it remains a soft preference rather than an enforced constraint, since some ingredients genuinely are used in odd quantities.

A fourth issue was cosmetic but recurring: a database entry's stored name is sometimes uninformative on its own (a barcode-derived placeholder, or a name truncated by a data-entry error upstream), which produced recipes referring to an ingredient by an unhelpful string. The prompt was extended to instruct the model to supply its own clear, human-readable name for a food when the database name is not informative, while still requiring the underlying code to be a real, resolvable database reference -- the human-readable name is cosmetic, but the code beneath it is still subject to the no-invented-foods contract in \Cref{sec:design-no-invented-foods}.

Finally, a session with no free-form request at all -- an empty query, corresponding to a user who simply presses through the initial prompt without asking for anything specific -- initially produced a slightly malformed prompt, since the query-formatting logic implicitly assumed some text would always be present. This was fixed by treating an empty query as its own explicit case, omitting the session-request section of the prompt entirely rather than inserting an empty one, since an omitted section reads to the model as ``there is no additional request'' more reliably than an empty one does.

\section{Structured output versus free text at the meal-idea handoff}
\label{sec:impl-meal-idea-structured}

The meal-idea agent's output is consumed in exactly one place: it is flattened into plain prompt text before the nutrition agent ever sees it, and nothing downstream parses a `MealConcept` as anything other than a string to be inserted into another prompt. This raised the question of why the meal-idea agent should produce a structured, schema-validated list of dish concepts at all, rather than simply free text, since the structure is discarded immediately afterwards. Structured output was kept regardless, for three reasons unrelated to downstream parsing. First, the schema-first framework's automatic retry-on-validation-failure (\Cref{sec:tools-agent-framework}) rejects an empty or degenerate concept before it ever reaches the nutrition agent, which free text has no equivalent safeguard against. Second, a schema field explicitly documented as requiring a concrete, specific dish name pushes the model considerably harder toward concrete suggestions (``oatmeal with berries'') than a prose instruction to ``suggest something specific'' does on its own. Third, structured output keeps the exact formatting of what reaches the nutrition agent's prompt under this system's control -- a fixed \textit{kind: dish name} pattern -- rather than at the mercy of whatever prose style the meal-idea model happens to produce, which would otherwise vary unpredictably between models and reduce the consistency of the ablation study's model comparison in \Cref{cha:results}.

\section{Keeping the ablation honest}
\label{sec:impl-ablation-honesty}

Because the ablation study's entire argument rests on attributing a measured difference in outcome to a specific toggled mechanism, any implementation detail that quietly differs between variants for a reason unrelated to that mechanism threatens the validity of the comparison. Two such risks were identified and closed off during implementation. First, the food knowledge base and its lookup tool are never among the toggled mechanisms (\Cref{sec:design-variant-config}); they are present, identically configured, in every variant, so that a change in outcome between variants can never be attributed to a difference in what the model was allowed to look up. Second, every variant in a given experimental run shares the same underlying pipeline instance and the same connection to the food knowledge base, rather than each variant constructing its own from scratch, so that no variant-specific initialisation difference (a different random seed for an index, a different cache state) could introduce a confound alongside the one flag actually being varied.

\section{Evaluation harness engineering}
\label{sec:impl-eval-harness}

Running a grid spanning several models, several ablation variants, several test scenarios and several repetitions each represents a nontrivial amount of paid model usage, and an interrupted run -- a transient network failure, a rate limit, or simply stopping the process to review intermediate results -- is a normal occurrence rather than an edge case. The run collector was built to be resumable: each individual (model, variant, scenario, repetition) combination is persisted to its own result file as soon as it completes, and re-invoking the collector recomputes only the combinations still missing a result file, so that a long grid can be run incrementally, over several sessions, without repeating (and repaying for) work already done. The same pipeline instance and food knowledge base connection are reused across every run sharing a model and variant, both for the honesty reason given in \Cref{sec:impl-ablation-honesty} and because reconstructing the food knowledge base's index from scratch for every single run would have dominated the harness's own running time. Finally, every run's token usage, request count and wall-clock time are recorded alongside its result, not because any evaluation metric in \Cref{cha:methodology} strictly requires them, but because they are the only way to characterise the computational overhead each mechanism imposes (\Cref{sec:results-overhead}) without having to re-run the grid purely to measure it.

\section{Judge stochasticity and the case for a second judge}
\label{sec:impl-judges}

The first version of the qualitative scoring stage did what the G-Eval pattern nominally prescribes: one judge model, one call per plan, one score. Two problems with that arrangement surfaced once enough runs had accumulated to look at them side by side. The first is that the judge is itself a sampled language model, so scoring the same unchanged plan twice does not reliably produce the same number; the score attached to a run was therefore carrying a component of pure judge noise that was indistinguishable, in any aggregate, from a real difference between the systems being compared. The second is subtler and more uncomfortable: the judge initially used belongs to the same model family as one of the configurations under comparison, which is exactly the situation in which the self-preference bias documented for this evaluation pattern~\cite{zheng2023judging} would inflate that configuration's scores. Neither problem is observable from inside a single-judge protocol, because a single judge provides nothing to disagree with.

Both were addressed at the protocol level rather than by attempting to make one judge behave better. Every plan is now scored three times by each judge, and the repetitions are averaged before a run's qualitative score is used anywhere, which turns judge sampling noise from an invisible contaminant into a quantity that shrinks predictably with repetitions. Alongside that, a second judge from an unrelated vendor scores every plan under the identical rubric. The two judges are never averaged together, which was a deliberate decision: averaging would hide precisely the disagreement the second judge was added to expose, so every judge-dependent metric is carried through the entire reporting pipeline as two parallel series and displayed side by side. What this bought is reported in \Cref{sec:results-stability}: the two judges disagree by a consistent offset while ranking configurations almost identically, so the comparative claims the thesis rests on survive a change of judge even though the absolute scores do not.

Making this affordable required the same resumability discipline as the run collector, one level down. Each (run, judge, judge repetition) triple is persisted to its own file under a per-judge directory, so scoring a grid with a newly added judge re-scores nothing that already exists, and an interrupted scoring pass resumes where it stopped rather than restarting. This mattered in practice: the second judge was introduced long after the first had finished scoring the entire grid, and adding it cost only the second judge's own calls.

\section{Paths not taken}
\label{sec:impl-dead-ends}

Three design directions were investigated in enough depth to be worth recording, and then set aside.

A full mixed-integer linear programming solver, of the kind reviewed in \Cref{sec:background-diet-optimisation} and combined with an LLM in related work~\cite{alkeyeva2026chatgpt}, was prototyped as a possible totaller replacement, on the reasoning that it could double as an optimiser rather than only a checker. It was abandoned for the reason already given in \Cref{sec:tools-aggregation}: by the time the totaller would run, the model has already committed to specific foods and quantities, leaving no unassigned decision variable for a solver to optimise over, only a sum left to compute exactly -- a role a solver is considerable engineering overkill for.

A multi-turn, interactive refinement mode -- in which a user could ask for a change to an already-generated plan in a follow-up message, rather than starting a new session -- was discussed early on as a natural extension of the reflection loop's revise-and-recheck pattern to a human reviewer instead of an automated critic. It was set aside for this thesis specifically because it is orthogonal to the ablation study's research question (none of the three hypotheses in \Cref{sec:introduction-goal} concern conversational continuity) while adding a substantial amount of state-management code with no corresponding measurement to justify it; it remains a natural direction for future, user-facing work (\Cref{sec:conclusions-future-work}).

Finally, having the language model itself generate a richer natural-language description of each food catalogue entry -- to be embedded in place of, or alongside, the raw database text used in \Cref{sec:impl-hybrid-search} -- was considered as a way to improve dense retrieval quality further, on the reasoning that a model-authored description could normalise inconsistent source data more gracefully than a fixed field-concatenation rule. It was not pursued within this thesis's scope, since it would have introduced a second, offline LLM-dependent build step with its own cost and consistency considerations onto the setup pipeline, and is noted instead as a candidate improvement in \Cref{sec:conclusions-future-work}.

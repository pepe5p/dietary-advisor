\chapter{System design}
\label{cha:design}

This chapter presents the architecture that follows from the requirements in \Cref{cha:vision} and the technology choices in \Cref{cha:methods-and-tools}. It describes what the system is designed to do, leaving the concrete difficulties met while building it to \Cref{cha:implementation}. The organising principle behind everything that follows is a division of labour by trustworthiness. The language model is given the work that requires interpretation and creativity -- reading a request, choosing dishes, writing a recipe, explaining a rationale -- and is deliberately denied the work where a plausible-looking wrong answer would be indistinguishable from a right one. Two structural devices enforce that boundary: an output schema with no field in which a nutrient value could be written, and a resolution step that turns the model's food references into database records before any arithmetic happens. The rest of the architecture -- the knowledge base, the retrieval strategy, the aggregator, the review loop -- follows from wanting those two devices to hold in every configuration the experiments will later switch between.

\section{Domain model: references versus hydrated plans}
\label{sec:design-domain-model}

Before the pipeline can be described, the two representations a meal plan takes inside it need naming, since the boundary between them is where the no-invented-foods contract is enforced. Two distinct representations of a meal plan will exist in the system, and the distinction between them is deliberate rather than incidental.

\begin{definition}[Agent plan]
    \label{def:agent-plan}
    An \emph{agent plan} is the structured output a language model produces: a set of meals, each a named recipe with a list of portions, where every portion is a triple of a database identifier, a human-readable name and a quantity in grams. It carries no nutrient field of any kind.
\end{definition}

\begin{definition}[Hydration and hydrated plans]
    \label{def:hydrated-plan}
    \emph{Hydration} resolves every identifier in an agent plan against the real food knowledge base and replaces it with that food's full database record, carrying its actual nutrient profile; the term is used in the sense it carries in data-mapping nomenclature, where hydrating a reference means filling it in with the record it points to. A \emph{hydrated plan} is the result of applying hydration to an agent plan.
\end{definition}

The totaller always operates on a hydrated plan (\Cref{def:hydrated-plan}), but when the model invokes it as a tool mid-generation the plan it receives is still an agent plan (\Cref{def:agent-plan}), as \Cref{fig:diagram-hydration} shows: the totaller hydrates it internally before summing, so the nutrient figures it returns are still computed from database records rather than from anything the model claims. This separation is what makes the no-invented-foods contract in \Cref{sec:design-no-invented-foods} structurally enforceable rather than merely a matter of prompt wording: an agent plan has no field in which a nutrient value could even be written down, so there is nothing for the model to hallucinate in the first place.

\section{The no-invented-foods contract}
\label{sec:design-no-invented-foods}

\ref{req:no-invented-nutrients}~requires that the system never report a nutrient figure that cannot be traced to a database entry and a specific quantity. This is enforced at two independent points, following the schema-first framework's output-validator hook chosen in \Cref{sec:tools-agent-framework}. First, the agent plan's schema (\Cref{sec:design-domain-model}) simply has no place to put a nutrient value: a portion is a code, a name and a gram quantity, so a model wishing to report an invented calorie count has no field to put it in and can only write it into free text, which is never parsed as nutrition data. Second, an output validator will run on every generated plan before it is accepted, attempting to resolve every referenced code against the real food knowledge base; a validator failure raises a structured retry request back to the model, listing exactly which codes did not resolve and reminding it that every code must be copied verbatim from a prior lookup result rather than guessed. This validator is the single point through which every agent plan -- whether from the initial generation, the reflection loop's refiner, or the totaller tool's own internal hydration step -- must pass, so the no-invented-foods guarantee holds identically regardless of which code path produced the plan.

\section{Architecture overview}
\label{sec:design-pipeline}

The system will be structured as a single, mostly linear pipeline invoked once per session, rather than as a long-running stateful service. \Cref{fig:diagram-pipeline} shows its stages. A runner receives the session request -- free text, possibly empty -- fetches the corresponding profile and its frozen targets from a profiles store, reads the variant flags that decide which optional mechanisms are active (\Cref{sec:design-variant-config}), and resolves a single model specification shared by every agent in the session. It then invokes a nutrition agent, which will compose the day's recipes and portions, calling out to the food knowledge base (\Cref{sec:design-food-db}) for every ingredient it uses and, when the totaller is enabled, to the totaller tool (\Cref{sec:design-totaller}) to check its own running totals mid-generation. Its output is an agent plan (\Cref{def:agent-plan}) that references food items by database identifier rather than describing their nutrient content itself (\Cref{sec:design-no-invented-foods}), and an output validator mechanically rejects any plan referencing an identifier that does not resolve in the real database before the plan is accepted. When the critique-and-refine loop is enabled, the validated plan will pass through a further review stage (\Cref{sec:design-reflection}) before hydration (\Cref{def:hydrated-plan}) turns it into the meal plan delivered to the user.

\section{Food knowledge base}
\label{sec:design-food-db}

The food knowledge base will combine the two bulk data sources chosen in \Cref{sec:tools-food-data} behind a single lookup interface, stored in the embedded analytical database chosen in \Cref{sec:tools-storage}. Each source will be materialised into its own flat table, since their native schemas differ too much to usefully merge (a packaged product's brand and ingredient list has no equivalent in a generic USDA entry, and vice versa), with every nutrient column normalised to a common unit and expressed per 100~g of food so that scaling by an arbitrary portion size is a single multiplication regardless of source. Every entry's identifier will be namespaced by its source (an Open Food Facts barcode or a USDA FoodData Central identifier) so that the two tables can share a single reference format without collision, and each table will carry both a full-text search index over its name and description fields and an embedding vector per entry, computed at build time with the embedding model chosen in \Cref{sec:tools-embeddings}, to support the hybrid search described next.

\section{Hybrid search and the lookup tool contract}
\label{sec:design-hybrid-search}

The lookup tool exposed to the nutrition agent will accept a batch of natural-language queries in a single call. Each query will be run against both data sources in parallel, and within each source, against both the lexical and the dense retrieval channels chosen in \Cref{sec:tools-retrieval}, fused by reciprocal rank fusion into one ranked list per source, as shown in \Cref{fig:diagram-retrieval}. The fused, ranked hits will be returned as a single structured result per query, carrying each candidate's identifier, name and per-100~g nutrient profile, so that the model can compare candidates and choose a portion size without a further round trip. Why the tool is batched, how many hits it returns, and what a single call costs against the context budget are implementation decisions, taken up in \Cref{sec:impl-tool-ergonomics}.

\section{Deterministic totaller}
\label{sec:design-totaller}

When enabled, the totaller will be reachable from two places: as a tool the nutrition agent (and, during the reflection loop, the refiner) may call mid-generation to check a proposed plan's running totals before finalising it, and as an independent post-hoc computation run by the evaluation harness on every hydrated plan regardless of whether the agent itself chose to call it. Both call sites will share the same underlying aggregation routine, using the exact rational arithmetic chosen in \Cref{sec:tools-aggregation}; the tool call accepts an agent plan and hydrates it internally before summing (\Cref{sec:design-domain-model}), so that the number the model sees mid-generation and the number the evaluation harness later scores the plan against are, by construction, computed identically.

\section{Agents and prompt architecture}
\label{sec:design-agents}

The pipeline will use a nutrition agent (and, structurally identical to it, a refiner used only inside the reflection loop) and, when the reflection loop is enabled, a tool-less critic. A single model specification -- a model identifier together with an optional reasoning-effort level, as motivated in \Cref{sec:tools-model-access} -- will be resolved once when a session starts and shared by the nutrition agent, the critic and the refiner. Why the ablation holds critic and generator on the same model, rather than giving the reviewer more capability, is taken up in \Cref{sec:impl-critic-design}. The fixed set of baseline dietary guardrails every agent works against -- distilled from public health guidance (energy from fat and free sugars, a sodium ceiling, a potassium floor, a minimum fruit-and-vegetable intake) -- is stated directly in the prompt rather than retrieved from an external source, because these particular guardrails apply near-universally to a healthy adult. Retrieving condition-specific guidance is left as further work (\Cref{sec:conclusions-future-work}). The prompt structure that carries the profile, the targets and these guardrails to all three agents is the subject of \Cref{sec:design-prompts}.

\section{Prompt design}
\label{sec:design-prompts}

The three agents just named all reason from a prompt, and the way that prompt is put together is itself a design decision rather than an incidental matter of wording. The guiding principle is that a prompt is ordinary text in the repository and is therefore governed by the same discipline as the code around it: it is not duplicated, and it is not relied upon where the same guarantee can be obtained mechanically. The decisions below follow from applying that principle to the nutrition agent, the critic and the refiner alike.

Each agent's prompt is split into two tiers. The system prompt carries everything fixed for the session -- the agent's role and an explicit denial of capability, its numbered hard rules, the baseline guardrails, the precedence between them, the ordered process it is to follow, and the output contract -- while the user turn carries only the session's data: the free-form request, the profile and the macronutrient targets rendered as JSON, and, for the two reviewing roles, the deterministic totals and the plan under review. The split is not cosmetic: the system prompt is a function of the configuration and the user turn a function of the session, so the profile data never sits among the instructions where a stray field could read as a rule.

Within the system prompt every agent follows the same fixed skeleton of blocks, in the same order: role and capability denial, numbered hard rules, baseline guardrails, precedence, implicit requirements, the process steps, and the output contract. The role block states the capability denial in as many words -- the agent has no ability to invent a food or estimate its nutrients -- so that the schema-level restriction of \Cref{sec:design-no-invented-foods} is legible in the prompt's language and not only in the type it must fill.

The prompts are deliberately zero-shot, carrying no worked example of a finished plan. The output is a large structured object, so an exemplar would cost thousands of tokens on every single call, and, more damagingly, would anchor the model on the specific foods and portions it happened to show -- a contamination the ablation study cannot tolerate, since its variants are meant to differ only by the mechanism that was toggled. The format-teaching role an exemplar would otherwise play is carried instead by the output schema and the descriptions attached to its fields, which the framework already surfaces to the model.

Nor does any prompt contain an explicit chain-of-thought instruction. Deliberation is treated as a provider-side control -- the reasoning-effort level of \Cref{sec:tools-model-access}, carried as part of the model identifier -- rather than as a phrase in the prompt of the kind reviewed in \Cref{sec:background-tool-use}; what structure the reasoning needs comes from the ordering of the process steps, and the \texttt{rationale} field is an output artefact rather than scratch space. Inviting the model to reason in prose about running nutrient sums would, in any case, invite exactly the free-hand arithmetic the totaller exists to remove.

Where rules conflict, the prompt states the precedence rather than leaving a flat list for the model to reconcile. A profile condition, a baseline guardrail and an explicit user request will not always agree, and sycophancy (\Cref{sec:background-llm-failure-modes}) means an insistent request tends to win regardless of what the prompt says; the design therefore fixes when a request legitimately wins -- for the specific item asked for -- and when it does not, requiring the rest of the day to compensate back towards the targets, instead of leaving that judgement to the model's disposition. In the same spirit the guardrails are phrased as the day's overall tendency rather than as a per-item ban.

A rule that more than one agent needs is written once and shared, never restated per agent. The baseline guardrail numbers live in a single fragment that both the nutrition agent's system prompt and the critic's checklist include, and the request-profile-targets head of every user turn comes from one shared composer. Were these duplicated, an edit to one copy -- lowering the sodium ceiling in the planner's prompt but not the critic's, say -- would leave the critic checking a plan against a limit the planner never targeted, and the disagreement would surface as a fabricated issue in the plan rather than as what it actually is: two copies of one rule that fell out of step. This is the same discipline that makes the totaller shared code between the runtime and the evaluation harness (\Cref{sec:design-totaller}).

Finally, the prompt is the last line of defence, not the only one. A contract that is already enforced mechanically is still restated in the prompt -- a food code must be copied verbatim from a lookup hit -- not because the sentence guarantees anything, but because stating it lowers how often the output validator has to reject a plan and pay for a retry; the guarantee itself stays in the validator (\Cref{sec:design-no-invented-foods}). This is the point at which this chapter's division of labour meets the theme of \Cref{cha:methods-and-tools}, that a validated schema beats a well-written prompt. It also widens what counts as a prompt: the validator's retry message, the tool descriptions, and the schema's field descriptions are all text the model reads, written for the model rather than for a developer, and are designed as deliberately as the system prompt itself. The critic's prompt shows the same care from the other side -- a reviewer told only to find problems will manufacture them, so an empty issue list is stated explicitly as the expected outcome for a good plan. The individual prompt refinements that reading real generated plans forced, together with how the prompt is assembled per ablation variant and for the empty-request case, are taken up in \Cref{sec:impl-prompt-fixes}.

\section{Critique-and-refine loop}
\label{sec:design-reflection}

When enabled, a generated (and validated) plan will be reviewed by the critic--refiner loop already drawn in \Cref{fig:diagram-pipeline}. The critic, given the plan, the user's profile and request, and -- when the totaller is also enabled -- the deterministic totals and any coverage warnings computed for it (\Cref{sec:impl-missing-nutrients}), will report a list of concrete issues, or an empty list if it finds none. An empty list ends the loop immediately with the plan as approved. A nonempty list is passed to a refiner, structurally identical to the nutrition agent and sharing the same food-lookup and totaller tools, which is instructed to address only the listed issues with minimal changes elsewhere; its revised plan is then sent back to the critic for another pass. This repeats until the critic reports no further issues or a fixed iteration budget of three passes is exhausted, whichever comes first; if the budget is exhausted with issues still outstanding, the loop returns the last refined plan rather than failing the session outright, so that a session never ends in an error purely because the critic and refiner did not converge in time.

\section{The ablation switch}
\label{sec:design-variant-config}

Because \ref{req:ablatable}~requires every grounding and review mechanism to be independently switchable, the pipeline will expose a single configuration object with one boolean flag per ablatable mechanism -- the totaller and the critique-and-refine loop -- read once at the start of a session and threaded through every stage that needs to know whether a given mechanism is active. Food knowledge base lookup is deliberately not one of these flags (\Cref{sec:vision-food-lookup-baseline}). This configuration object is the single source of truth the evaluation harness in \Cref{cha:methodology} sets when it runs the ablation grid, so that a given run's variant label is derived mechanically from exactly the flags that were set for it, rather than tracked separately and potentially inconsistently. Each agent's system prompt is assembled from the same flags that decide which tools are registered, so an ablated variant never describes a tool it no longer has: turning the totaller off drops the tool and, in the same step, removes the rule that tells the agent to verify its totals.

\section{Package layering}
\label{sec:design-layering}

The codebase will be split into three packages with a strict, one-directional dependency rule: a runtime package, \texttt{dietary\_advisor}, containing only what is needed to serve a session; a setup package containing one-off, offline provisioning code (downloading and building the food knowledge base from the bulk exports chosen in \Cref{sec:tools-food-data}); and an evaluation package containing the ablation harness described in \Cref{cha:methodology}. The setup and evaluation packages may import from the runtime package, but the runtime package may never import from either of them. \Cref{fig:diagram-runtime} shows the runtime at module level. Inside it, a command-line entry point sits over a session pipeline that owns the ablation switch and drives the agents, the critique-and-refine loop, hydration, the totaller and the food knowledge base reader. The two outer packages lean on that stack very differently: setup reuses only the runtime's embedding loader, to embed each food record with the same model the session later queries with, whereas the evaluation harness drives the whole pipeline and reuses hydration and the totaller so that the number it scores a plan against is computed by the same code the session used (\Cref{sec:design-totaller}). The harness's own internal structure, and the three arrows it draws into this stack, are shown in \Cref{fig:diagram-layering}.

The harness's trustworthiness rests on a precise division between the runtime code it reuses and the evaluation logic it owns.\label{sec:design-eval-reuse} Three cross-package dependencies land on individual runtime modules: the case runner drives the very same pipeline a real session uses, and the validation stage recomputes each plan's totals with the same hydration and totaller code the runtime and the agent's own mid-generation checks use. Everything the runtime must not know about -- the scenarios, the judges, the metrics, and the reporting -- the harness owns itself, and the runtime never imports the evaluation package in return. This is what lets the harness never re-implement any logic whose result it is trying to measure, while the judge, at the other extreme, is handed a plan carrying no nutrient numbers at all and no indication of which variant or model produced it, and the targets it is scored against are frozen on the profile outside the pipeline under test.

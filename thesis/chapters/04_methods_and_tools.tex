\chapter{Review of methods and tools}
\label{cha:methods-and-tools}

Every choice below is presented as a trade-off among named alternatives rather than as a default; where a rejected alternative would have been a reasonable choice under different priorities, that is stated explicitly. Two themes recur. The first is a strong preference for offline, version-pinned artefacts over live services: a food database queried dozens of times while composing a single plan cannot depend on a rate-limited network call, and a result set that changes underneath a running experiment cannot be reproduced. The second is that a component's correctness guarantees matter more than its raw performance wherever a wrong answer would be indistinguishable from a right one, which is why exact arithmetic beats fast arithmetic and a validated schema beats a well-written prompt. Concrete model identifiers belong to the experiments and appear in \Cref{cha:results}.

\section{Implementation platform}
\label{sec:tools-platform}

A dietary planning agent spends most of its wall-clock time waiting on network calls to language model providers and on local food knowledge base queries; it is not compute-bound in the way a training workload is. This makes the choice of implementation language secondary to the choice of ecosystem: whichever language has the most mature tooling for typed agent orchestration, structured LLM output validation, and data-science-adjacent tasks such as building an embedding index is preferable to whichever is nominally faster at raw computation. Python was chosen on this basis. Its ecosystem includes mature LLM client libraries for every major provider, mature data-validation libraries (used throughout for the structured contracts described in \Cref{sec:tools-agent-framework}), an embedded analytical database with first-class Python bindings (\Cref{sec:tools-storage}), and a scientific-computing stack sufficient for the exact-arithmetic aggregation and plotting needs of the evaluation harness. A statically typed, compiled language would have offered better raw throughput and stronger compile-time guarantees, but at the cost of a materially less mature ecosystem for exactly the two things this project spends the most engineering effort on: LLM tool-calling orchestration and structured output validation.

\section{Agent framework}
\label{sec:tools-agent-framework}

Three broad approaches were available for orchestrating a language model that must call tools and produce a validated, typed output.

\begin{itemize}
    \item \textbf{Raw provider SDKs.} Every major LLM provider ships a client library that exposes tool-calling and structured-output primitives directly. Building the orchestration loop (deciding when to call a tool, parsing the provider-specific tool-call format, validating the final output, retrying on a schema violation) by hand on top of these primitives offers maximum control and no framework dependency, but means re-implementing the same conversation-loop, retry and validation logic for every provider a system wants to support, since each provider's tool-calling wire format differs in nontrivial ways.
    \item \textbf{General-purpose orchestration frameworks (e.g.\ LangChain, LangGraph).} These frameworks abstract over multiple providers and add higher-level constructs for composing multi-step or graph-structured agent workflows, at the cost of a large surface area of abstractions -- many of them aimed at use cases such as long-running stateful graphs or complex branching pipelines -- that this system's comparatively simple, mostly linear pipeline (\Cref{sec:design-pipeline}) does not need. Their structured-output support has also historically been an add-on to a chat-completion abstraction rather than the primary interface.
    \item \textbf{A schema-first, type-centric agent library (pydantic-ai).} This category of framework treats a strongly typed data-validation model as the primary interface for both an agent's structured output and its tool signatures, delegates only the provider-specific request and response formatting to per-provider adapters, and exposes an explicit output-validator hook that can reject a structurally valid but semantically wrong response and trigger an automatic retry with an explanatory message appended to the model's context.
\end{itemize}

Of the three, the pydantic-ai library  was chosen. Its output-validator hook is the mechanism the no-invented-foods contract in \Cref{sec:design-no-invented-foods} depends on directly: every generated plan is validated against the real food database before it is accepted, and a validation failure produces a targeted retry rather than a silent pass-through. Its provider adapters also make \ref{req:provider-agnostic}~(provider-agnostic model access) close to free, since switching the underlying model is a configuration change rather than a code change.

\section{Model access}
\label{sec:tools-model-access}

Three ways of obtaining language model inference were considered: direct per-provider API access, a routing or aggregation service that exposes many providers' models behind one API, and self-hosted inference of an open-weight model. Direct per-provider access offers the lowest latency and the tightest control over provider-specific features, but ties a codebase to one vendor's request format per model family, which conflicts with \ref{req:provider-agnostic}. Self-hosted inference removes any dependency on an external provider and any per-token cost, but requires provisioning and maintaining GPU infrastructure sized for a model capable enough to be a meaningful comparison point, which is a substantial infrastructure investment orthogonal to this thesis's research question. A routing service that exposes a single, provider-agnostic API surface over many hosted models was chosen instead: it lets the model comparison in \Cref{cha:results} span multiple providers' model families without maintaining separate integration code for each, and lets the ablation grid be re-run against a different model purely by changing a configuration value.

Contemporary reasoning models expose a second, independent control alongside the choice of model: a \emph{reasoning-effort} setting that governs how much internal deliberation the provider allows before the model commits to an answer, typically as a small ordinal scale from minimal to very high. This setting is independent of model choice: it trades latency for additional deliberation within one model rather than swapping the model out, and \ref{req:provider-agnostic}~requires it to be configurable rather than left at whatever each provider defaults to. It is therefore treated as part of the model identifier throughout the system, so that a model and an effort level travel together as one configuration value, and it becomes the second axis of the capability comparison in \Cref{sec:methodology-model-grid}.

\section{Food composition data access}
\label{sec:tools-food-data}

Any grounding strategy of the kind described in \Cref{sec:background-tool-use,sec:background-self-correction} is only as good as the knowledge base it grounds against. Two large, openly available food composition sources cover complementary needs. The USDA FoodData Central Foundation Foods and SR Legacy datasets\footnote{\url{https://fdc.nal.usda.gov/} (accessed 2026-09-06).} provide laboratory-analysed nutrient profiles for generic, minimally processed foods (a raw carrot, a whole egg, rolled oats) with broad international applicability but no coverage of specific branded or packaged products. Open Food Facts\footnote{\url{https://world.openfoodfacts.org/} (accessed 2026-09-06).} is a crowd-sourced, international database of branded, packaged products, contributed by volunteers who photograph and transcribe product labels; it has far denser coverage of the kind of packaged food a consumer actually buys, but far less consistent completeness of any individual nutrient field, since it depends on what a given contributor chose to transcribe. How the two sources are combined, and how an absent field is treated without silently becoming a zero, is taken up in \Cref{sec:design-food-db,sec:impl-missing-nutrients}.

Each of the two can be accessed either through a live query API or through a bulk, offline export. A live API avoids storing and maintaining a local copy of a large dataset and always reflects the provider's latest data, but introduces a network dependency and rate limits into every single food lookup a nutrition agent makes -- and a system whose agent may issue dozens of lookups while composing one meal plan cannot tolerate that on either latency or reliability grounds. A commercial nutrition data API was also considered as a third option, offering a single unified interface over multiple sources, but was rejected on licensing and reproducibility grounds: a bulk offline export can be version-pinned and redistributed alongside the evaluation results it produced, whereas a commercial API's licence terms and rate limits make that kind of reproducibility difficult to guarantee. Bulk, offline exports of both USDA FoodData Central and Open Food Facts were chosen instead, downloaded once during a setup step (\Cref{sec:design-food-db}) and never queried live at request time.

\section{Storage and indexing engine}
\label{sec:tools-storage}

The food knowledge base needs to support three access patterns at once: exact and fuzzy text search over food names and descriptions, similarity search over an embedding vector per food, and simple relational lookups by an identifier. Three engines were compared for this role.

\begin{itemize}
    \item \textbf{SQLite with the FTS5 extension.} Widely available, zero-configuration, and sufficient for lexical full-text search, but with no first-party vector similarity index; approximate nearest-neighbour search would have to be bolted on through a separate extension of uneven maturity.
    \item \textbf{PostgreSQL with the pgvector extension.} A mature relational database with both full-text search and vector similarity search available as extensions, and the natural choice for a system that expects concurrent multi-client write traffic -- but that is a server process to provision, configure and keep running, which is disproportionate infrastructure for a dataset that is built once during setup and only ever read at request time.
    \item \textbf{DuckDB~\cite{raasveldt2019duckdb}, an embedded, single-file analytical database with first-class full-text search and vector similarity search extensions.} Requires no separate server process, ships with a mature Python binding, and is optimised for the read-mostly, analytical-style queries (fuzzy text match plus vector distance, fused into a single ranked result set) this system performs.
\end{itemize}

DuckDB was chosen. Its single-file, embedded deployment model matches a food database that is built once offline and shipped read-only with the application, and its native full-text and vector-index extensions cover both retrieval channels needed in \Cref{sec:tools-retrieval} without a second database engine.

\section{Hybrid retrieval strategy}
\label{sec:tools-retrieval}

Searching the food knowledge base for, say, ``mozzarella'' needs to succeed whether the query is an exact lexical match for a product name or a semantic near-match for a differently worded description. Two retrieval families address these cases with complementary strengths and weaknesses.

Lexical ranking (in particular the BM25 scoring function, a term-frequency and inverse-document-frequency-based ranking algorithm refined over decades of information-retrieval research~\cite{robertson2009probabilistic}) is fast, requires no learned model, and excels at exact or near-exact term matches, but is blind to synonymy: a query for ``courgette'' will not match a product labelled only ``zucchini''. Dense retrieval, in which both the query and every catalogue entry are embedded into the same vector space and ranked by similarity, captures exactly this kind of semantic relationship, but can under-rank an entry that is a close lexical match yet embeds slightly off-distribution, and is more expensive to compute and index than a lexical score.

Combining the two rankings requires a fusion strategy. Score-based fusion (a weighted sum of the two raw similarity scores) requires the two scores to be normalised onto a comparable scale, which is fragile because BM25 and cosine-similarity scores have different, corpus-dependent distributions with no natural shared unit. Reciprocal rank fusion sidesteps this by discarding the raw scores entirely and combining only each result's \emph{rank} within its own list, using the formula $\mathrm{RRF}(d) = \sum_i \frac{1}{k + \mathrm{rank}_i(d)}$ summed over each ranking list $i$ a document $d$ appears in, with $k$ a small constant (conventionally 60) that discounts the influence of very low ranks; this method was shown to consistently outperform both individual rankings and a more complex, ranking-committee alternative across several retrieval benchmarks, without requiring any training data or score calibration~\cite{cormack2009reciprocal}. Reciprocal rank fusion over a lexical (BM25) and a dense-embedding ranking was chosen for exactly this rank-only, calibration-free property.

\Cref{fig:diagram-rrf-example} works the formula through on a single query. The behaviour it exposes is what recommends the scheme beyond calibration-freedom: a candidate both channels rank highly, rather than one a single channel ranks first, is the one most likely to be the food the query meant, and a rank-only fusion prefers it without being told to. \Cref{sec:design-hybrid-search} describes the scheme as it is wired into the lookup tool.

\section{Embedding model and vector index}
\label{sec:tools-embeddings}

Dense retrieval requires an embedding model to turn a food description into a vector, and an index structure to search that vector space efficiently at scale. For the index, Hierarchical Navigable Small World graphs (HNSW) were chosen over an exact brute-force scan: HNSW organises indexed vectors into a multi-layer proximity graph that allows a query to be answered in logarithmic rather than linear time relative to catalogue size, at a small and tunable cost in recall~\cite{malkov2018efficient}, and is available as a native index type inside the storage engine chosen in \Cref{sec:tools-storage}, avoiding a second, separate vector database.

For the embedding model itself, three broad options existed: a large hosted embedding API, called over the network for every document and every query; a small, English-only local model; and a larger, multilingual, locally run model. A hosted API was rejected for the same latency and reproducibility reasons as a live food-data API in \Cref{sec:tools-food-data}. A small English-only model would have been the cheapest to run locally but would have degraded on the many non-English product names and descriptions present in an internationally sourced packaged-food catalogue. A multilingual embedding model capable of dense, sparse and multi-vector retrieval from a single set of weights, trained specifically to generalise across more than a hundred languages and across document lengths from a short phrase to a long passage~\cite{chen2024bgem3}, was chosen instead, run locally through an optimised inference runtime so that embedding an entire catalogue during setup and embedding a query at request time both stay off the network entirely.

\section{Deterministic nutrient aggregation}
\label{sec:tools-aggregation}

Once a set of food quantities has been resolved to real database entries, their nutrient contributions must be summed. Three ways of performing this sum were considered. Ordinary floating-point arithmetic is what a language model would produce if left to do the sum itself, and is also what a naive re-implementation in the aggregator would default to; it is fast, but accumulates rounding error across the dozens of additions and unit-scaling multiplications a full day's meal plan requires, and that rounding error is exactly the kind of small, silent numeric drift a system built to eliminate LLM-introduced numeric drift should not reintroduce at the verification layer itself. A full mixed-integer linear programming solver, of the kind reviewed in \Cref{sec:background-diet-optimisation}, would allow the aggregator to double as an optimiser rather than a pure calculator, but was rejected as disproportionate to this system's needs: the language model already proposes concrete recipes and quantities, so there is no unassigned decision variable left for a solver to optimise over by the time the aggregator runs, only a sum to compute exactly. Exact rational arithmetic, in which every quantity is represented as an exact fraction rather than a finite-precision float, was chosen instead: it costs a small, bounded amount of extra computation per operation and completely eliminates rounding error from the aggregation step, so that any residual error between a delivered and a targeted nutrient total is attributable to the plan's food choices and quantities, never to the arithmetic that scored them.

\section{Self-correction scheme}
\label{sec:tools-self-correction}

\Cref{sec:background-self-correction} identified two points on a spectrum of self-correction designs: a critique-and-refine loop grounded purely in a model's own re-reading of its output, and one grounded in feedback from an external tool. A fully tool-grounded critic, in the style of \textsc{CRITIC}~\cite{gou2024critic}, was considered for this system's reflection loop, with the critic itself able to issue further food-database lookups; it was set aside in favour of a narrower design in which the critic is tool-less but is still shown the deterministic totaller's output when the totaller is enabled, combining most of the grounding benefit of an external tool with a simpler, more predictable critic role that reviews a fixed set of inputs rather than one that can itself trigger further, potentially unbounded retrieval. \Cref{sec:design-reflection} describes the resulting critique-and-refine loop, and \Cref{cha:results} reports how much of the accuracy gain attributed to grounding survives when the critic, rather than only the generator, is given access to the computed totals.

\section{Evaluation tooling}
\label{sec:tools-evaluation}

The evaluation harness needs three capabilities distinct from the runtime system it evaluates: a way to drive a large, resumable grid of pipeline runs across models, configurations and test scenarios; a way to score both the deterministic, numeric aspects of a run and its open-ended, natural-language aspects; and a way to turn the resulting scores into readable summaries and figures. The grid-execution and scoring stages were built as a separate command-line application from the runtime system, following the package-layering rule that keeps evaluation-only code out of the runtime path (\Cref{sec:design-layering}); the qualitative scoring stage reuses the same schema-first agent framework chosen in \Cref{sec:tools-agent-framework}, configured with an explicit per-criterion rubric and following the G-Eval pattern described in \Cref{sec:background-evaluation}. The judge protocol itself is specified in \Cref{sec:methodology-qualitative}.

\chapter{Experimental methodology}
\label{cha:methodology}

Because the claims this thesis makes are comparative -- one configuration is more accurate than another -- almost all of the methodological effort goes into making sure that a measured difference can only be attributed to the thing that was deliberately changed. The grid varies one factor at a time from a fixed baseline, and everything is repeated on two independent axes because neither the system nor the instrument measuring it is deterministic (\Cref{sec:methodology-stability}).

\begin{definition}[Cell]
    \label{def:cell}
    A \emph{cell} of an experimental grid is one combination of language model, system variant and scenario.
\end{definition}

\section{Research questions}
\label{sec:methodology-research-questions}

The hypotheses in \Cref{sec:introduction-goal} translate into three concrete research questions.

\begin{description}
    \item[RQ1] By how much does enabling the deterministic totaller reduce energy and macronutrient error?
    \item[RQ2] By how much does enabling the critique-and-refine loop improve adherence to the stated constraints and preferences, and what effect does it have on energy and macronutrient error, on its own and on top of the totaller?
    \item[RQ3] How does plan quality vary with the choice of language model and with its reasoning-effort level, and can raising the effort level substitute for a stronger model?
\end{description}

RQ1~and RQ2~are answered by a single \emph{component ablation} experiment, referred to throughout this thesis as \textbf{Experiment~1} (\Cref{sec:methodology-variants}), which holds the language model fixed and varies only the totaller and reflection flags. RQ3~is answered by a separate \emph{model comparison} experiment, \textbf{Experiment~2} (\Cref{sec:methodology-model-grid}), which holds the system configuration fixed at its strongest setting and varies the model and its reasoning-effort level together. These two names label every result and every generated figure in \Cref{cha:results}.

\section{Experiment 1: component ablation}
\label{sec:methodology-variants}

The component ablation experiment uses the four-way grid implied by the two independent flags in \Cref{sec:design-variant-config}, shown in \Cref{fig:diagram-variants}. Food knowledge base access is not one of the varied flags (\Cref{sec:vision-food-lookup-baseline}): \emph{baseline} here denotes a system that already looks up real foods and simply lacks the two optional mechanisms under study.

Each of the four variants is run against every scenario in \Cref{sec:methodology-scenarios} with one fixed language model, giving 60 runs in total for this experiment. The following parameters are held constant across both experiments: three repetitions per cell, three scoring passes per judge per run, and a critique-and-refine loop budget of three refinement passes (\Cref{def:iterations}).

\section{Experiment 2: model and reasoning-effort grid}
\label{sec:methodology-model-grid}

The model comparison experiment fixes the system at the full variant and varies the generating model instead. Two things are varied at once, deliberately: the base model, and the reasoning-effort level that model is asked to run at. Four base models are compared, each at three effort levels, giving twelve configurations. Where a provider's default effort already falls at one of the three levels being compared, that default is used as the level rather than re-requesting it explicitly, so a configuration is identified by a model together with the effort it actually ran at.

Two properties of this design matter for interpreting the results. Within one base model the three configurations differ only in effort, so a difference between them is attributable to deliberation alone. Across base models, by contrast, the effort labels are each vendor's own, with no guarantee that one vendor's \emph{high} corresponds to another's -- so the aggregate comparison across effort levels in \Cref{sec:results-effort} groups vendor-specific labels into three coarse buckets and should be read as an indication of direction rather than as a calibrated measurement. Each of the twelve configurations is run against all five scenarios, giving 180 runs. Fifteen of these coincide exactly with the full-variant cell of the ablation experiment and are stored and scored once, so the two experiments together comprise 225 distinct runs.

The reasoning-effort setting is applied only to the agents whose output affects plan correctness -- the nutrition agent, the critic and the refiner -- as described in \Cref{sec:design-agents}. The judges are not affected by it: they run at their own providers' defaults regardless of which configuration produced the plan they are scoring, so that the measuring instrument does not change as the object of measurement does.

\section{Scenarios and profiles}
\label{sec:methodology-scenarios}

Each evaluated run pairs a fixed user profile with a scenario: an optional free-form session request and, where applicable, a set of scenario-specific soft criteria scored by the qualitative judges (\Cref{sec:methodology-qualitative}). Five scenarios were selected for the main experimental grid, listed in \Cref{tab:methodology-scenarios}. They were chosen to differ in what they demand of the system rather than to sample a population: one asks for nothing beyond a coherent day of food, two set a hard exclusion against an explicit user request for something that would violate it, and two impose interacting chronic conditions whose dietary guidance pulls in several directions at once.

\section{Structure of the evaluation harness}
\label{sec:design-eval-harness}

The evaluation harness is a command-line application of its own, structured as shown in \Cref{fig:diagram-layering}: a case runner drives the grid, a scoring stage applies the judges, and a reporting stage turns stored scores into figures and a metrics file. Two design principles run through every part of it. The first is that every reported number must be reproducible from durable artefacts on disk rather than from the transient state of a single long-running process, so each stage reads what the previous one wrote and any stage can be repeated on its own. The second is that no component ever scores its own work: the code that generates a plan, the code that computes its deterministic totals, and the model that judges its quality are kept apart. \Cref{fig:diagram-eval-flow} traces the data through the three stages and the artefact stores that connect them; \Cref{fig:diagram-layering} shows the same harness at the level of code modules and the runtime modules it reuses (\Cref{sec:design-eval-reuse}).

\subsection{Three stages with three different costs}
\label{sec:design-eval-stages}

The harness is deliberately split into three separately invoked commands -- case collection, scoring, and reporting -- rather than a single end-to-end run, because the three differ sharply in what they cost and how often they are run. Generating a plan is slow and paid for in model tokens; scoring a stored plan is also paid, but entirely independent of how the plan was generated; and reporting is free and can be rerun whenever a figure or a summary is refined. Fusing them would force the expensive stages to rerun whenever a cheap one changed. Keeping them separate means the interface between stages is the artefact store on disk rather than an object in memory, so each stage can be run, interrupted, and repeated without its predecessor being present in the same process.

\subsection{The run specification as the unit of work and identity}
\label{sec:design-eval-runspec}

The atom the whole harness is organised around is the \emph{run specification}: a language model, a system variant, a scenario, and a repetition index. Every run specification derives a stable, filesystem-safe key from those four fields, and that key names every artefact belonging to the run. The full grid is enumerated in code as the set union of the two experiments' specifications, so the combination both experiments share -- the full variant of the fixed model -- exists as a single specification and is therefore collected and scored only once. Because a specification's variant and model are the very same configuration objects the runtime consumes (\Cref{sec:design-variant-config}), a run's recorded label cannot drift away from the configuration that actually produced it: the label is derived mechanically from the flags that were set, not tracked separately.

\subsection{An artefact store written only on success}
\label{sec:design-eval-store}
\label{sec:impl-eval-harness}

Each unit of work is persisted as a single JSON file named by its key: one file per collected run, and one file per judge per scoring repetition under a per-judge directory. All artefact paths are derived in one place, so the layout is defined once rather than reconstructed at each call site. There is no database, no lock, and no central manifest of progress: the set of work still to do is simply the difference between the grid the code enumerates and the files already present on disk. A file is written only after its stage succeeds, so a failed or interrupted unit leaves no artefact behind and is naturally retried on the next invocation. Each record is self-describing -- it repeats the variant flags, the frozen targets, the plan, and the run's telemetry -- so it can be read and interpreted without the grid that produced it.

Running a grid spanning several models, several ablation variants, several test scenarios and several repetitions each represents a nontrivial amount of paid model usage, and an interrupted run -- a transient network failure, a rate limit, or simply stopping the process to review intermediate results -- is a normal occurrence rather than an edge case. Re-invoking the collector therefore recomputes only the combinations still missing a result file, so that a long grid can be run incrementally, over several sessions, without repeating (and repaying for) work already done. The same pipeline instance and food knowledge base connection are reused across every run sharing a model and variant, both so that no variant-specific initialisation difference (a stale cache, a re-seeded index) can creep in as a confound alongside the one flag actually being varied, and because reconstructing the food knowledge base's index from scratch for every single run would have dominated the harness's own running time. Every run's token usage, request count and wall-clock time are recorded alongside its result, because they are the only way to characterise the computational overhead each mechanism imposes (\Cref{sec:results-overhead}) without having to re-run the grid purely to measure it.

\subsection{Separating the judge-independent half from the judge-dependent half}
\label{sec:design-eval-two-halves}

A run's evaluation splits cleanly into a half that does not depend on any judge and a half that does, and the harness stores them separately. The deterministic energy and macronutrient error is computed at collection time, using the runtime's own hydration and totaller so that it is measured against a real total rather than anything the model claimed, and written onto the run record itself. The qualitative verdicts are stored apart, one file per judge per repetition, and the two halves are joined only in the reporting stage. Adding, removing, or rescoring a judge therefore regenerates no plan and cannot change any quantitative number, because the quantitative number never lived in a judge's record in the first place.

\subsection{Judges as a registry}
\label{sec:design-eval-judges}

A judge is nothing more than a key paired with a model identifier, sharing one common rubric with every other judge; the only thing that varies between judges is the model. Every layer beneath the registry iterates over it rather than naming individual judges, so introducing a second judge propagates by itself into the per-judge artefact directories, the aggregation, the figures, and the metrics file. This registry is the structural device that carries the rule, specified in \Cref{sec:methodology-qualitative}, that judge-dependent metrics are never averaged across judges: they are carried through as one parallel series per registered judge from the store all the way to the reported columns.

\subsection{Aggregation in layers}
\label{sec:design-eval-aggregation}

Turning stored artefacts into reportable numbers happens in four layers, each a pure function over the layer below. The first averages a judge's repeated verdicts for one run into a single verdict, suppressing the judge's sampling noise. The second joins that averaged verdict with its run record. The third summarises the joined records per (model, variant) group into the per-variant means. The fourth groups records for the figures and computes their dispersion -- the standard error drawn as an error bar, and the spread of \Cref{def:spread}, which is computed only where all of a group's repetitions are present. Because nothing but the deterministic per-run error is aggregated at collection time, changing how a metric is summarised means rerunning only the free reporting stage.

\subsection{Reporting: one declaration per metric}
\label{sec:design-eval-reporting}

A reported metric is declared exactly once, as a record carrying its key, its title, the function that extracts its value from a scored run, whether it depends on the judge, and an optional predicate restricting it to the variants where it is meaningful (the refinement-pass count only for variants that run the reflection loop, the count of model-initiated totaller invocations only where the totaller is enabled). That single declaration drives the metric's figure and its entry in the machine-readable metrics file together, so a metric cannot be plotted one way and summarised another.

\section{Quantitative scoring: energy and macronutrient error}
\label{sec:methodology-quantitative}

The quantitative scoring stage measures how closely a plan's delivered energy and macronutrient totals match their targets, using the same deterministic aggregator described in \Cref{sec:design-totaller} to compute the delivered values -- independently of whether the totaller tool was available to the model during generation, so that even a baseline-variant plan's accuracy is judged by a real, exactly computed total rather than by anything the model claimed.

For each tracked nutrient $n$ (energy, protein, carbohydrates, and fat) with a positive target, a signed relative error is computed as
\[
    \mathrm{rel}_n = \frac{\mathrm{actual}_n - \mathrm{target}_n}{\mathrm{target}_n} \times 100\%,
\]
where $\mathrm{actual}_n$ is the deterministically computed total for a hydrated plan and $\mathrm{target}_n$ is the profile's frozen target for that nutrient. Each run is then summarised by the mean absolute and the mean squared value of $\mathrm{rel}_n$.

\begin{definition}[Macro error]
    \label{def:macro-error}
    Let $N = \{\text{energy}, \text{protein}, \text{carbohydrate}, \text{fat}\}$ be the aggregated nutrients with a positive target for the run's profile. The \emph{macro error} of a run is the mean absolute relative error
    \[
        \mathrm{MAE\%} = \frac{1}{\left| N \right|} \sum_{n \in N} \left| \mathrm{rel}_n \right| .
    \]
    It is non-negative and unbounded above, and is zero exactly when every aggregated nutrient meets its target, so lower is better. It does not depend on a judge.
\end{definition}

\begin{definition}[Squared macro error]
    \label{def:macro-error-squared}
    With $N$ as in \Cref{def:macro-error}, the \emph{squared macro error} of a run is the mean squared relative error
    \[
        \mathrm{MSE\%} = \frac{1}{\left| N \right|} \sum_{n \in N} \mathrm{rel}_n^2 .
    \]
    It shares the properties above, but weights a single badly missed nutrient far more heavily than an even spread of small misses. It is always named explicitly where it is used, and likewise does not depend on a judge.
\end{definition}

Expressing the error relative to its target rather than in absolute nutrient units is what keeps a single figure comparable across nutrients measured on very different scales -- kilocalories against grams of fat, for instance. Both statistics are reported because the failure this evaluation is most interested in is the occasional badly wrong plan rather than a uniform drift away from target, and the two separate those cases. Because both are computed from the stored plan by a deterministic routine, they do not depend on the judges at all, and are identical no matter which judge's records they are read from.

\section{Qualitative scoring: the judge protocol}
\label{sec:methodology-qualitative}

Everything not captured by an energy or macronutrient number -- whether a recipe is physically coherent, whether a stated allergen was actually avoided, whether an explicit session request was honoured without violating a harder constraint -- is scored by an LLM-as-a-judge stage following the G-Eval pattern described in \Cref{sec:background-evaluation}: a judge model is given an explicit natural-language rubric per criterion and asked to produce both a score and a short justification, rather than a bare number with no accompanying reasoning.

Every run is scored on one criterion present in all scenarios (whether the generated recipes are physically and logically coherent) plus every scenario-specific soft criterion listed for it in \Cref{sec:methodology-scenarios} -- for instance, whether a DASH-appropriate sodium-to-potassium balance was targeted, or whether a stated food preference was honoured without including a disliked food. Each criterion is scored on a continuous $[0, 1]$ scale, and the two judged metrics reported in \Cref{cha:results} are built from those scores as follows.

\begin{definition}[Soft score]
    \label{def:soft-score}
    Let $K$ be the set of soft criteria applying to a run: the recipe-coherence criterion present in every scenario, plus that scenario's own criteria (\Cref{sec:methodology-scenarios}). A judge scores each $k \in K$ with $s_k \in [0, 1]$, and the \emph{soft score} of one verdict is
    \[
        \mathrm{soft} = \frac{1}{\left| K \right|} \sum_{k \in K} s_k .
    \]
    The value carried into every figure and table is the mean of this over the three verdicts that judge returned for the run. It lies in $[0, 1]$, higher is better, and it is judge-dependent: it is reported once per judge and never averaged across judges.
\end{definition}

\begin{definition}[Safety score]
    \label{def:safety-score}
    The \emph{safety score} is a single always-scored rubric field in $[0, 1]$ recording whether the plan respected the profile's allergen exclusions and diet pattern, averaged over a judge's three verdicts exactly as the soft score is. It is deliberately not a member of $K$, so a serious safety failure cannot be diluted by the soft-score average. Each verdict also returns a list of the concrete \emph{safety violations} the judge identified, in free text. Higher is better, and it is judge-dependent.
\end{definition}

The judges are explicitly instructed not to penalise a plan for a missing micronutrient figure that the underlying food data itself does not cover, so that the coverage gaps described in \Cref{sec:impl-missing-nutrients} are not double-counted as a plan-quality failure on top of being flagged by the totaller's own coverage warnings.

\label{sec:impl-judges}
The first version of the qualitative scoring stage was the naive one: a single judge model, one call per plan, and the bare integer it happened to sample. G-Eval does not read off a single sampled integer but a probability-weighted score computed over the judge's output token distribution~\cite{liu2023geval}, but the judge APIs used here expose no token probabilities, so this first version simply took the sampled score at face value. Two problems with that arrangement surfaced once enough runs had accumulated. The first is that the judge is itself a sampled language model, so scoring the same unchanged plan twice does not reliably produce the same number. The second is that the judge initially used belongs to the same model family as one of the configurations under comparison, which is exactly the situation in which the self-preference bias documented for this evaluation pattern~\cite{zheng2023judging} would inflate that configuration's scores. Neither problem is observable from inside a single-judge protocol.

Both were addressed at the protocol level rather than by attempting to make one judge behave better:

\begin{itemize}
    \item \emph{Two judges, from different vendors.} Every plan is scored independently by both. One of them belongs to the same family as one of the compared configurations, which is exactly the situation self-preference bias would exploit; the other has no such overlap with any compared configuration. A family-specific bias therefore cannot hide, because it would appear as a divergence between two judges reading the same plans against the same rubric.
    \item \emph{Repeated scoring.} On the second of the two repetition axes, the verdicts a judge returns for a run are averaged before its qualitative score is used anywhere. Because the judge API does not expose token probabilities, this averaging also serves as a Monte Carlo estimate of G-Eval's probability-weighted score, which is the substitute G-Eval itself adopts whenever the scoring model's token probabilities are unavailable~\cite{liu2023geval}; it suppresses judge sampling noise without concealing how large it was.
    \item \emph{No averaging across judges.} Judge-dependent metrics -- the soft score and safety score -- are carried through the whole reporting pipeline as two parallel series and always reported side by side. Collapsing them into one number would destroy precisely the disagreement the second judge exists to reveal.
\end{itemize}

Each (run, judge, judge repetition) triple is persisted to its own file under a per-judge directory, so scoring a grid with a newly added judge re-scores nothing that already exists, and an interrupted scoring pass resumes where it stopped rather than restarting. This mattered in practice: the second judge was introduced long after the first had finished scoring the entire grid, and adding it cost only the second judge's own calls. What the protocol revealed is reported in \Cref{sec:results-stability}.

\section{Stability metrics}
\label{sec:methodology-stability}

Repetition happens on two independent axes, and keeping them apart matters for reading the numbers that follow. Every cell of the grid is planned three times, which samples the generating model's own nondeterminism. Each of those runs is then scored three times by each judge, which samples the judge's. The first axis is quantified here as run-to-run variability; the second is averaged away as described in \Cref{sec:methodology-qualitative}.

Two further quantities describe how repeatable a result is, rather than how good it is, and both are reported per judge.

The first is \emph{run-to-run variability}: how much the same configuration's soft score moves when the identical request is planned again from scratch. Because the repetitions of one cell (\Cref{def:cell}) differ only in the language model's sampling, the dispersion within a cell isolates that sampling noise.

\begin{definition}[Cell spread]
    \label{def:spread}
    The \emph{spread} of a cell is the mean absolute deviation of its soft score about the cell's own mean:
    \[
        \bar{s}_c = \frac{1}{R} \sum_{r=1}^{R} s_{c,r},
        \qquad
        d_c = \frac{1}{R} \sum_{r=1}^{R} \left| s_{c,r} - \bar{s}_c \right|,
    \]
    where:
    \begin{itemize}
        \item \( c \) -- a cell (\Cref{def:cell}),
        \item \( R \) -- the number of repetitions of a cell,
        \item \( s_{c,r} \) -- the soft score one judge awarded to repetition \( r \) of cell \( c \),
        \item \( \bar{s}_c \) -- the mean soft score of cell \( c \),
        \item \( d_c \) -- the spread of cell \( c \).
    \end{itemize}
    It is non-negative, expressed on the same $[0, 1]$ scale as the soft score, and lower means more repeatable. Like the soft score it is reported per judge.
\end{definition}

\begin{definition}[Run-to-run variability]
    \label{def:variability}
    The \emph{run-to-run variability} of a model, and of an experiment as a whole, is the mean cell spread over the relevant cells:
    \[
        V_m = \frac{1}{\left| C_m \right|} \sum_{c \in C_m} d_c,
        \qquad
        V = \frac{1}{\left| C \right|} \sum_{c \in C} d_c,
    \]
    where:
    \begin{itemize}
        \item \( C_m \) -- the set of cells whose language model is \( m \),
        \item \( C \) -- the set of all cells of the experiment,
        \item \( V_m \) -- the variability reported for model \( m \),
        \item \( V \) -- the pooled variability of the experiment.
    \end{itemize}
    Only cells with all of their repetitions scored contribute, so that no cell's spread is computed from a partial sample.
\end{definition}

The size of $V$ relative to the differences between configurations is what matters for this thesis: a spread of the same order as those differences means they cannot be read as real.

The second is the agreement between the two judges. Because both score every plan under an identical rubric, any systematic difference between their means is a property of the judges rather than of the plans, and any difference in how they \emph{rank} configurations is the more serious concern, since every comparative claim in \Cref{cha:results} depends on ranking. Both are reported in \Cref{sec:results-stability}.

\section{Operational metrics}
\label{sec:methodology-operational}

Four further figures are recorded per run without requiring any scoring step.

\begin{definition}[Iterations]
    \label{def:iterations}
    The \emph{iterations} of a run is the number of refinement passes the critique-and-refine loop completed. It is zero when reflection is disabled for the variant and also when the critic approved the first draft outright, and it is capped at the configured loop budget, three throughout this evaluation. It does not depend on a judge.
\end{definition}

\begin{definition}[Totaller calls]
    \label{def:totaller-calls}
    The \emph{totaller calls} of a run is the number of times the model invoked the deterministic totaller tool of \Cref{sec:design-totaller} while planning, counted across the nutrition agent and the refiner. It is zero when the totaller is disabled for the variant, and it counts only model-initiated invocations: the totals the critic is handed automatically (\Cref{sec:design-reflection}) and the aggregation the scoring stage performs itself (\Cref{sec:methodology-quantitative}) are not model decisions and are excluded. It is unbounded above and does not depend on a judge.
\end{definition}

\begin{definition}[Elapsed time]
    \label{def:elapsed-time}
    The \emph{elapsed time} of a run is its wall-clock duration in seconds, from the start of the planning pipeline to the delivered plan, including every model request and tool call the run made along the way. It does not depend on a judge.
\end{definition}

\begin{definition}[Token spend]
    \label{def:token-spend}
    The \emph{token spend} of a run is the number of tokens billed across every model request the run made, split into four additive categories matching the provider usage fields: cache read, which the provider served from a prompt cache rather than recomputing; input, the remainder of the billed input; output, the remainder of the billed output after reasoning tokens are set aside; and reasoning, the thinking tokens already included in the billed output. It does not depend on a judge and plays no role in scoring a plan's quality. No monetary cost is reported anywhere in this thesis: converting tokens into money requires per-model prices that change without notice and differ by routing provider, which would make any figure quoted here both unverifiable and out of date within months.
\end{definition}
